# v0.1.3 findings

Changes since v0.1.2 (released 2026-11-02), with causes. Issues carry the details.

- **Plugin support (issue #49).** Habilis Terminal loads plugins written against a public SDK (`src/HabilisTerminal.Plugins.Sdk`, packed as NuGet `HabilisTerminal.Plugins.Sdk` 1.0.0). Design: `docs/plugins.md`.
  - Discovery in `<app>\plugins\<id>` and `%LOCALAPPDATA%\HabilisTerminal\plugins\<id>`, a `plugin.json` per plugin, one `AssemblyLoadContext` per plugin with the host's SDK shared; failures are listed in F9 > Options > Plugins.
  - Plugin panels reuse the file panel: entries become `FileEntry` rows; a `PanelExtension` adds custom columns, groups sorted first, row tones and sorting by a custom column. Layouts on Ctrl+1..., plugin sort keys in Ctrl+F12, header clicks sort custom columns. A null `CellValue.SortValue` means a missing value (sorted last).
  - Keys: Enter / `..` / Ctrl+PgUp navigate the plugin and leave it at its top; F3 (plugin view, else a temporary copy), F5 / F6 both ways, F7, F8, plugin commands (their keys take precedence), F11 plugin menu, Alt+Shift+F9 plugin list and configuration, Ctrl+L plugin info.
  - Entry points: F11, the drive menu's Plugins group, folder history, and the command line: a PSReadLine Enter handler reports `prefix:...` lines (bare `sqs:` too) through an `open-address` OSC message instead of running them; the user's own Enter function is kept.
  - The shell stays in the local folder the plugin was opened from; the saved state keeps that folder too.
  - Fixed while checking: Enter, `..`, Ctrl+\ and the context menu first went to the local file system (`demo:\documents`), because those edits had not applied (CRLF files); F11 and the other plugin picks did not give focus back after Esc; a bare `sqs:` ran in PowerShell.
- **Plugins (`plugins/`, issues #46, #47, #48).** Built outside the app's solution against the SDK package from the local feed (`tools/plugins/Build-Plugins.ps1`): `Habilis.Aws.Common` (profiles incl. role and SSO, regions, plain-language errors), SQS queues (`sqs:`), SageMaker training jobs (`sm:`), S3 browser (`s3:`), and a network-free demo (`demo:`). AWS SDK for .NET 4.0 (Apache 2.0). 158 plugin tests with fakes; no real AWS calls were made.
- **Checked in test copies** (`New-TestCopy.ps1 -WithPlugins`): with the demo plugin every panel feature (columns, groups, tones, layouts, header sort, F3, F5 both ways, F7, F8, a command, Ctrl+L, leaving, history); with the AWS plugins loading, F11, `sqs:` / `sm:` / `s3:` with a missing profile (plain message, back to the local folder), the plugins list and the SQS settings form.
- **Not checked:** the AWS plugins against a real account (the owner's step; each README has a test plan); SageMaker prices (from memory, basis stated, user-overridable); high DPI.

## After v0.1.4
- **Shipped plugins failed to load (issue #60).** The release job's `dotnet publish -p:Version=0.1.4` is a global property, so it also set the SDK assembly's version (0.1.4.0); the plugins reference SDK 1.0.0.0 and the load context returned `null` for the SDK, which made the default context refuse the older version: "Could not load file or assembly 'HabilisTerminal.Plugins.Sdk, Version=1.0.0.0'". Local publishes without `-p:Version` hid it. Fix: the SDK csproj pins its own `AssemblyVersion` / `FileVersion` / `PackageVersion` (from `SdkVersion`), and `PluginLoadContext` returns the host's SDK assembly whatever version a plugin asks for (compatibility stays with the manifest's `sdk`). Guards: a test that the SDK assembly version equals `HostSdkVersion`, and a release step that fails when the published SDK carries the app version. Checked with a release-like publish (`-p:Version=0.1.9`) plus the plugins: Alt+Shift+F9 lists all four without errors, F11 lists their items, the demo panel opens.

## After v0.1.5
- **AWS plugins: only the first one opened could use role and SSO profiles (issue #61).** The owner's S3 browser worked; SQS and SageMaker then failed with "Assembly AWSSDK.SecurityToken could not be found or loaded". AWSSDK.Core finds its STS / SSO clients by reflection, taking the first assembly with that name in `AppDomain.CurrentDomain.GetAssemblies()`, which spans every load context, so the second plugin got the first plugin's copy and could not use it (any failure is reported as "could not be found"). Fix in `Habilis.Aws.Common/AwsClients.cs`: role profiles get a `RefreshingAWSCredentials` that calls this plugin's own `AmazonSecurityTokenServiceClient` (chained roles too), and the SSO / SSO-OIDC clients are registered with `GlobalRuntimeDependencyRegistry`, which is per AWSSDK.Core copy and checked before reflection. Checked with a fake role profile and an unreachable endpoint (`AWS_ENDPOINT_URL=http://127.0.0.1:9`): before the fix, S3 then SQS gave the owner's error; after it, S3, SQS and SageMaker each reach the AssumeRole call. Not checked: SSO profiles and a real account (verify).

  - F3 text mode (#56): text files up to `viewer.textModeMaxMB` (10) in a read-only AvalonEdit inside `ViewerPage`; F4 hex switches to the paged `ViewerView` at the caret line. AvalonEdit theming moved to `TextEditorTheme`.

  - Archives (#51) on 7z.dll 26.04 (`third_party/7-Zip`, per RID): own interop (`Core/Archives`), shown as a plugin panel with a built-in `LoadedPlugin`. Reading, F5/F6 both ways, F8, F7; updates write a temp copy next to the archive, then replace it. Found in UI checks: (1) zip re-reads files it stores uncompressed, so added files must stay seekable (`SourceStream` reopens on seek); (2) a 7z.dll object created on the UI thread (STA) fails from the pool with E_NOINTERFACE (no proxies), so every open / dispose runs on the pool; (3) a non-IO failure left the temp copy behind, now any failure deletes it.
